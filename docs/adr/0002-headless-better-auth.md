# 2. better-auth used headlessly, behind our own contract

- Status: accepted
- Date: 2026-08-09

## Context

better-auth ships an HTTP handler that can be mounted directly, and there is a
community NestJS integration (`@thallesp/nestjs-better-auth`) that mounts it
for you. Mounting it would expose routes such as `/api/auth/sign-in/email`
whose shapes are defined by better-auth, not by `packages/contracts`.

## Decision

Never mount better-auth's HTTP handler. Implement `/auth/*` as ordinary
ts-rest routes in `apps/api` that call better-auth's server API
(`auth.api.signUpEmail`, `signInEmail`, `signOut`, `getSession`) internally.

## Consequences

- `packages/contracts` remains the only place request/response shapes live,
  which is the point of the architecture.
- The community integration's Fastify support is beta; this avoids depending
  on it at all.
- better-auth's own tables (`user`, `session`, `account`, `verification`) are
  generated by its CLI into `packages/db`. They are deliberately *not* merged
  with the `users` business table — different identifier format, no shared
  columns, different lifecycle. `authUserSchema` in the contracts package is
  therefore separate from `userSchema`.
- Cookies must be bridged manually from better-auth's response back onto the
  Fastify reply — see [ADR 0003](0003-cookie-bridge-not-res-decorator.md).
- Cost: any better-auth feature we want (social login, 2FA, magic links) needs
  a contract route added by hand rather than appearing automatically.
